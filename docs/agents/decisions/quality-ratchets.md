# Quality ratchet decisions

These records explain three gates ported from paulnsorensen/milknado: the file-size ratchet
(`.github/scripts/check_file_lengths.py`), the whole-symbol dead-code gate (`.github/scripts/check_dead_code_coverage.py`),
and the coverage gate (`.github/scripts/check_coverage.py`).
milknado runs them in `just check-llm` as `file-size`, `dead-code-coverage`, and the project and diff coverage steps.
ADR-004 records how the CI shards split the skillz lanes by committed test durations.

## Records

### ADR-001: The file-size budget is a one-way ratchet  [status: accepted]

- **Context:** milknado holds `src/` files to 300 lines. A larger file needs a waiver with a measured ceiling and a reason. A PR may raise a ceiling when it gives a reason. At adoption, 24 of the 132 `packages/*/src` files here have more than 300 lines.
- **Decision:** Keep the 300-line budget and the per-file waivers in `[tool.skillz.file-size]` of `pyproject.toml`. Unlike milknado, `check` also fails when a waiver is stale, when its file fits the budget, or when its file is shorter than its ceiling. `check_file_lengths.py tighten` lowers each ceiling to the measured count and removes the waivers that are no longer needed. It never raises a ceiling.
- **Consequences:** A change that shrinks a waived file runs `tighten` in the same change, as with the depth ratchet. Only a human raises a ceiling, and the PR says why. The gate runs as the lanes `file-size` and `file-size-tests`.

### ADR-002: One coverage lane checks the combined data of every pytest lane  [status: accepted]

- **Context:** milknado runs one pytest suite with `--cov-fail-under` and then `diff-cover`. Here, five pytest lanes measure four packages, and CI runs the two skillz lanes in six shard jobs.
- **Decision:** Each pytest lane runs as `coverage run --parallel-mode -m pytest` on the source of every workspace package, because the tests of one package also run the code of another (the skillz tests call `wedge.layer_import_names`). `[tool.coverage.run] patch = ["subprocess"]` measures the xdist workers and the CLI tests that start Python subprocesses. Each process writes `<lane>[.<i>of<n>].cov.<host>.<pid>.<random>` to `$GATE_COVERAGE_DIR`, else to a directory below the gate temporary root. No process combines or removes these files before the `coverage` lane. A gate removes stale lane data from its directory when it starts, so a nested gate (such as the `test_run_gate.py` fakes) must not inherit `GATE_COVERAGE_DIR`: it removed the files of live test subprocesses, and the failed save put a traceback on their stderr. After every other lane passes, the `coverage` lane runs `check_coverage.py`. It combines the lane files, then checks the project floor (`[tool.coverage.report].fail_under`), whole-symbol dead code, and diff coverage (`[tool.skillz.coverage].diff_fail_under`, 95 as in milknado). The diff base resolves as the slice guard base does (architecture-gates ADR-005). When `GATE_SKIP` names a pytest lane, the `coverage` lane does not run. In CI, the gate job and each shard upload their lane files, and the `coverage` job combines them.
- **Consequences:** `just build` runs the full check locally. CI reports it as the `coverage` check, a required check of the `main-protection` ruleset. The job has no `if:`, so it is skipped when the gate or a shard fails; GitHub counts a skipped required check as passing, so `coverage` stays required together with `gate (just ci)` and `skillz tests`. The diff check prints the measured line count and says so when a diff has no measured source line. The project floor is the measured total at adoption, rounded down. The gate asks for a raise when the total reaches one point above the floor; it does not raise the floor itself.

### ADR-003: Whole-symbol dead code reads only `packages/*/src`  [status: accepted]

- **Context:** The milknado gate maps one `src/` tree to module names and exempts `[project.scripts]` targets of one package.
- **Decision:** A module name is the path below `packages/<name>/src`. Exemptions are the `[tool.vulture].ignore_decorators` patterns, the `[project.scripts]` targets of every workspace package, and the `module:qualname` entries in `[tool.skillz.dead-code].allow`. Each allow entry carries a comment that says why no test reaches the symbol.
- **Consequences:** A function that only a built `.pyz` archive or a live harness runs needs a test, a `# pragma: no cover`, or an allow entry. A function whose whole body is on its `def` line cannot be flagged.

### ADR-004: CI shards split the skillz lanes by committed test durations  [status: accepted]

- **Context:** The six CI shards split the two skillz lanes by collection position modulo six (`.github/scripts/pytest_shard.py`). That split ignores the duration of each test, so one slow module can make one shard the longest job.
- **Decision:** pytest-split replaces the modulo plugin. With `GATE_SHARD=<n>/6`, `run_gate.py skillz` runs each lane with `--splits 6 --group <n> --splitting-algorithm least_duration`. The split reads `packages/skillz/.test_durations`, a committed JSON map of test id to seconds. pytest-split reads and writes one `--durations-path`, so each lane starts from a copy of the committed file below `$GATE_COVERAGE_DIR/durations/`. `--store-durations --clean-durations` then replaces the copy with the durations of this shard's tests. The `coverage` job merges the six shard uploads with `merge_durations.py` into the `test-durations` artifact. The merge fails when a test is in two files. A test that the file does not name gets the mean duration of the named tests.
- **Consequences:** The committed file is the one reviewable data source for the shard split. The seed file gives each collected test the same value (0.1 s), so the first split balances by test count. A refresh replaces the file with the merged CI artifact; until then, renamed and new tests get the mean. The `refresh test durations` workflow (`.github/workflows/refresh-test-durations.yml`) does the refresh each Monday and on `workflow_dispatch`. It checks out main, downloads the `test-durations` artifacts of the last three green `validate` push runs on main, and runs `refresh_durations.py` (self-test lane `durations-refresh-tests`). Per-file wall time under `-n 4` varies about 0.5× to 2.5× from run to run, so one run is not a stable measure. The script keeps the test ids of the newest run and gives each id its maximum seconds over the runs. It writes that map to the file when the map differs, so the split reads a conservative basis. With three runs, it also passes every run to the ADR-006 `tighten`, so each file's ceiling comes from its slowest run; with fewer, it does not tighten. On no change, the run logs `no change` and opens no PR. On a change, it force-pushes `chore/refresh-test-durations` and opens or updates one PR against main. The repository has no bot token or GitHub App, so the workflow uses `GITHUB_TOKEN`. Until the owner allows GitHub Actions to create pull requests, the job pushes the branch and fails with `REFRESH-NO-PR`. A PR from `GITHUB_TOKEN` starts no workflow run, so a human closes and reopens it to start the checks. Local `just build` and `just ci` leave `GATE_SHARD` unset and run each lane whole. The selection runs in each xdist worker; it is deterministic, so every worker of one shard selects the same tests.

### ADR-006: A one-way time ratchet holds each skillz test file to a CI wall-time ceiling  [status: accepted]

- **Context:** No gate stopped a change that adds a slow test file. ADR-004 gives the merged CI durations of every skillz test as the `test-durations` artifact. ADR-005 holds the collected case counts by the same one-way ratchet; wall time also needs a bound, but it varies with host load. The local host often runs other gates and agents (spec `test-suite-cost-gates` F-2).
- **Decision:** `.github/scripts/check_test_durations.py` sums the stored durations (setup + call + teardown) of each test file, keyed by the node-id prefix before `::`. `[tool.skillz.test-time]` in `pyproject.toml` sets a default ceiling of 20 s. A file needs a waiver in `[tool.skillz.test-time.exceptions]` when 2.5 × its measured seconds, rounded up, is above the default; the waiver ceiling is that value. The measure is the slowest of the runs given: `tighten` accepts one or more durations files and keeps each file's slowest run. `check` fails on a file above its ceiling. `check` reports a ceiling that can go down, but it does not fail on it, because one fast run is not a stable measure. `tighten` lowers each improved ceiling, removes the waivers that the default covers, and never raises one. The CI `coverage` job runs `check` on the merged file after the merge. Each shard lane also writes a JUnit report (`<lane>.<i>of<n>.xml`) beside its durations file, and `--collected` sums the `tests` counts of these reports. `check` then fails with a coded message when the merged file is missing (`TIME-MISSING`), malformed (`TIME-INVALID`), or empty (`TIME-EMPTY`), when no report gives a count (`TIME-NO-COUNT`), or when the file holds fewer test ids than the shards selected (`TIME-SHORT`). Locally, `run_gate.py` runs `report` on the committed `packages/skillz/.test_durations` after the lanes, as the `test-time-report` step. It prints the ten slowest files, the breaches, and the improved waivers, and it never fails the gate.
- **Evidence:** The spec chose 1.5 × headroom. Two CI runs (41417007579 and 41419094652) gave per-file ratios of 0.51 to 2.52 between the runs, with a median of 1.19, over the 88 files above 5 s. With 1.5 ×, the second run broke 7 ceilings from the first. The likely cause is that, after the duration-based split, slow tests run side by side under `-n 4`, and their wall time depends on what else runs. The user approved 2.5 × on 2026-11-02.
- **Consequences:** Missing or short data cannot pass the CI check. The first waivers come from the slowest of the two runs, both before the prune PR, so many ceilings are loose. The `refresh test durations` workflow (ADR-004) passes the durations of the last three green runs on main to `tighten` on each refresh, so one fast run cannot lower a ceiling too far. A test that a PR adds or renames has no committed duration, but the CI check measures it in the same run. A human raises a ceiling, and the PR says why. The self-test lane is `durations-check-tests`, and the CI step is `Check test times` in the `coverage` job.
