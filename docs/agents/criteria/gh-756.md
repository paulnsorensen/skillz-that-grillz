# gh-756: measure the baseline before search

Source: https://github.com/paulnsorensen/skillz-that-grillz/issues/756

| id | kind | criterion | verified by |
| --- | --- | --- | --- |
| AC-1 | test | WHEN `run` executes the baseline pass THE SYSTEM SHALL score the seed 2 times on each scored case of the train, validation, and holdout splits. |  |
| AC-2 | test | WHEN the baseline pass records a holdout outcome THE SYSTEM SHALL record it under the `baseline` arm, SHALL keep the `holdout-isolated` runner check passing, and SHALL keep that outcome out of every reflection prompt and every search reuse. |  |
| AC-3 | test | WHEN the baseline pass ends THE SYSTEM SHALL list every scored case id of every split under `exposed` in `run.json` and in `report.json`; a later search, gate, or export report SHALL show no case outside that list. |  |
| AC-4 | test | WHEN the baseline pass ends and the user did not pass `--search` THE SYSTEM SHALL write `report.json` in the run directory, SHALL print the report summary, SHALL exit with status 0, and SHALL make no search, reflection, or gate call. |  |
| AC-5 | test | WHEN the system writes `report.json` THE SYSTEM SHALL include, for each case, the split, the score of each repeat, and each unmet criterion with its level and the judge's reason; the family means for each split; the `criteria_flags` and `zero_cases` fields that `export` writes; and the calls, seconds, and tokens for each role. |  |
| AC-6 | test | WHEN a train or validation family is at or above the headroom ceiling THE SYSTEM SHALL name that family in the baseline report, also when the contract sets `statistics.min_token_saving`. |  |
| AC-7 | test | WHEN `run` is called without `--search` on a run directory that holds a finished baseline THE SYSTEM SHALL print the same summary, SHALL exit with status 0, and SHALL make no model call. |  |
| AC-8 | test | WHEN `export` is called on a run directory that holds only a baseline THE SYSTEM SHALL refuse it, as `export` refuses every run that is not `complete` today (`run/_export.py:259-260`), and the message SHALL name `report.json`. |  |
| AC-9 | test | WHEN the cases are not approved THE SYSTEM SHALL stop with `cases-unapproved`, and the stop data SHALL hold the case question, the case hash, and the estimate of the baseline plan. |  |
| AC-10 | test | WHEN one call gives the matching `--approve-cases` hash and an `--approve-budget` that covers the baseline estimate THE SYSTEM SHALL start the baseline pass with no more questions before it. The search budget question of AC-12 is a later, separate question. |  |
| AC-11 | test | IF a call gives the matching case hash and no budget approval, THEN THE SYSTEM SHALL stop with `budget-unapproved` and the same estimate. |  |
| AC-12 | test | WHEN the user passes `--search` for a run directory that holds a baseline THE SYSTEM SHALL score no train or validation seed outcome again, SHALL apply the `cases-too-easy` check of AC-16, and SHALL then stop with `budget-unapproved` and the search estimate until the user approves that budget. |  |
| AC-13 | test | WHEN a `--search` call starts on a run directory that already holds a finished baseline, passes the check of AC-16, and gives an `--approve-budget` that covers the search estimate THE SYSTEM SHALL record the new budget, the new estimate, and a new start time in `run.json`, and SHALL run the search, the gate, and the replay. |  |
| AC-14 | test | WHEN the gate scores the baseline arm after a baseline pass THE SYSTEM SHALL reuse the 2 recorded holdout repeats and SHALL score only the missing repeats. |  |
| AC-15 | test | WHEN the user passes `--search` for a new run directory THE SYSTEM SHALL ask the first question for the baseline plan, SHALL run the baseline pass and write `report.json`, and SHALL then apply the steps of AC-12 in the same order; the `--approve-budget` of a call that ran the baseline pass SHALL NOT count as the search budget approval, whatever its amount, so that call always ends at the `budget-unapproved` stop with the search estimate or at the `cases-too-easy` stop. |  |
| AC-16 | test | WHEN the user passes `--search` and the `cases-too-easy` rule of today applies (autoimprove ADR-018: one train or validation family is at or above the headroom ceiling and the contract sets no `min_token_saving`) THE SYSTEM SHALL stop with `cases-too-easy` and the baseline report, and SHALL make no search call. |  |
| AC-17 | test | WHEN `run` is called on a run directory whose `plan_mode` is `search` THE SYSTEM SHALL resume that run as today, with or without `--search`. |  |
| AC-18 | test | WHEN `run` opens a run directory that an older engine prepared THE SYSTEM SHALL refuse it with the existing older-run diagnostic and SHALL make no model call. |  |
| AC-19 | process | WHEN a user reads the skill's `autoimprove` procedure THE SYSTEM SHALL describe the baseline as the default result, `--search` as the opt-in step, and one approval question for the default run; the `skillz-self-update` procedure SHALL pass `--search`. | Wave 3 review of the published procedures. |
| AC-20 | test | WHEN the journey gate checks an `--approve-budget` THE SYSTEM SHALL accept a `cases-unapproved` stop of an earlier turn that holds an `estimate`, under the same conditions as a `budget-unapproved` stop (`skills/skillz/evals/gates/journey.py:7-10`), and the journey cases of the skill SHALL expect the one-stop approval. |  |
